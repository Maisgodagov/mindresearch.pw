# Подключение нового теста

## Карта файлов

- `apps/api/src/public-methods/catalog.json`: редакционный исходный список, не вся исследовательская библиотека.
- `model.ts`: схема контента, разрешённые slug/code, получение бланка `definition`, валидация и `calculate`.
- `apps/api/src/data/`: бланки/реестр; `apps/api/src/scoring/`: чистые функции расчёта. Найди фактический источник через `rg`, не угадывай имя файла.
- `schema.ts`: начальное создание публикаций из списка через `INSERT IGNORE`.
- `repository.ts`: отдельно draft/published/revision; `router.ts`: API, редактор, доступ по cookie.
- `seo.ts`, `render.ts`, `static-pages.ts`: общие метаданные, HTML без JavaScript, sitemap и файловые страницы из опубликованных данных.
- `apps/web/src/containers/PublicMethods/`: `Catalog`, `MethodPage`, `index` (прохождение/результат), `card`, `Admin`, `types`, `shared`.
- `scripts/generate-public-test-images.cjs`: изображения OG 1200×630 для статьи и каталога.

## 1. Проверка базы и источников

Найди code, бланк и scorer. Проверь, что инструмент активен и не отозван. Обнаружение code в реестре не доказывает наличие корректного автоматического подсчёта. Сопоставь число и порядок вопросов, варианты ответа, обратные пункты, формы по полу/возрасту, пропуски, нормы и диапазоны со статьёй/руководством. Если scorеr требует дополнительных данных, публичный сценарий должен явно их собирать или выбрать обоснованную фиксированную форму. Не выбирай пол/возраст скрыто.

Для источников предпочитай оригинальную публикацию, страницу автора/издателя, русскую адаптацию и проверку её свойств. Вторичные каталоги могут помогать найти первоисточник, но не заменяют проверку. Не копируй чужую статью целиком. У свободного оригинала перевод может иметь отдельные права.

## 2. Контент записи

Добавь запись, сохранив текущую схему. Основные поля:

- `slug`: стабильный английский kebab-case без версии и query; один URL на одну выбранную методику/адаптацию. При смене уже опубликованного slug нужен постоянный редирект.
- `code`, `version`: конкретные бланк и формула; не меняй их через редактор статьи.
- `name`, `abbreviation`: научное название и реальная аббревиатура.
- `title`: человеческий заголовок, понятный без знакомства с терминологией.
- `topic`, `minutes`: фактическая тема и разумная оценка времени по числу/сложности вопросов.
- `intro`: кратко, что человек исследует и какой результат получит.
- `seoTitle`, `seoDescription` (необязательные): уникальные сниппеты. Если отсутствуют, общий генератор использует название и intro. Не вставляй набор ключей.
- `audience`, `instruction`: кому применима именно эта версия и как отвечать.
- `sections`: смысл шкалы, авторы/версия, расчёт, интерпретация, применение в исследовании. Сохраняй полезный текст, не раздувай под условное число слов.
- `limitations`, `rights`, `sources`: реальные ограничения, условия использования, проверенные HTTPS-источники.

Текущая `MethodPage.tsx` дополнительно содержит `methodBackground` для зарегистрированных тестов. Для нового slug добавь проверенные 1–2 предложения с авторами/адаптацией либо расширь модель общим полем и перенеси туда существующие записи. Не оставляй вводную без авторства. Карточка использует `titles` в `card.ts` с fallback; при необходимости добавь короткий заголовок.

## 3. Схема и расчёт: важные ловушки

В `contentSchema` сейчас закрытые enum для зарегистрированных slug и code. Добавь соответствующие значения. Не снимай ограничения произвольно: редактор публикаций не должен получить возможность назначить случайный бланк.

`definition` сверяет code/version с зарегистрированным исходным каталогом. Подключи точный бланк отдельной явной веткой или небольшим реестром, если он действительно упрощает расширение. Бланки перечислены в явном словаре по code; неизвестный code отклоняется. Новый тест нельзя просто вписать в JSON: подключи его бланк в словаре.

В `calculate` RSES/GSES/MSPSS используют свои scorers, а SWLS/SHS/BIT — существующий `calculateConfigurableScores` с конкретной конфигурацией. Новый code требует корректного scorer и преобразования к `PublicResult`. Ветку неизвестного code следует отклонять, а не считать чужим алгоритмом. Не вводи универсальный подсчёт суммой для методик, где его нет.

`answersSchema` сейчас целые числа 0–7, `saveSchema.position` — до 100. Проверь совместимость нового бланка. Расширение этих границ допустимо лишь вместе с проверкой каждого ответа по вариантам конкретного снимка; простое снятие ограничений не решает многовариантные и текстовые вопросы.

Результат:

- первая `scale` — обоснованный общий показатель; если общего показателя у методики нет, до подключения измени модель/карточку так, чтобы он не выдумывался;
- каждая шкала: `label`, `value`, `min`, `max`, `explanation`;
- объяснение общее и для подшкал; никакого автоматического диагноза и вымышленных процентилей;
- дробные показатели не округляй до расчёта; форматирование вывода отдельно;
- неизвестные/неполные ответы не заменяй нулями.

## 4. Публикации и история

`INSERT IGNORE` добавляет **новые** записи; изменение JSON не обновляет существующие опубликованные тексты в БД. Для обновления существующей статьи используй редактор/API с актуальной revision или явную узкую миграцию. Никогда не перезаписывай массово все опубликованные статьи при деплое.

Исходный каталог сейчас автоматически становится published при первой миграции. Не добавляй в него незавершённый/неразрешённый материал перед production. Если нужен отложенный выпуск, предусмотрите draft-only миграцию/непубличное хранение.

При сохранении publish/unpublish синхронизируются HTML и sitemap; draft не должен менять их. При ошибке файлового экспорта проверь фактическую revision: запись могла сохраниться раньше ошибки, не повторяй запрос со старой revision вслепую. Старые прохождения сохраняют snapshot текста/бланка/результата и не меняются от редакционной правки.

## 5. Проверки

- крайние баллы min/max, обратные пункты, дробные подшкалы, несколько известных ручных примеров из источника;
- недопустимый вариант, пропущенный вопрос, конфликт revision, недоступный/неопубликованный slug;
- гость: каталог → статья → согласие → ответы → перезагрузка/продолжение → завершение → карточка → удаление;
- другой браузер и UUID без cookie не читают/не меняют/не удаляют прохождение;
- guest/researcher не имеют доступа к редактору;
- desktop/mobile, PNG 1080×1920, длинные названия и все подшкалы. Не допускай отрицательный радиус или исчезновение шкал при расширении компоновки;
- `npm run build`, релевантные API/UI-тесты. UI-прохождение выполнять на `preview.ts`/memoryRepository, не на ответах реальных пользователей.

## Дополнительные опорные примеры

- SWLS: `satisfaction-with-life`, `test_2480`, модуль `method-2462.ts` (номер файла не совпадает с code), перевод Елшанского и соавт. 2015, сумма 5–35.
- SHS: `subjective-happiness`, `test_2451`, модуль `method-2433.ts`, форма Осина/Леонтьева, публикация 2020. Среднее 1–7, обратный пункт 4 по формуле 8 − ответ; все единицы дают 2,5.
- BIT: `brief-thriving`, `test_59`, `bitRu.ts`, адаптация Костенко/Набиевой/Лебедевой 2025, сумма 10–50, а не среднее оригинала.
- Условия некоммерческого использования SWLS/SHS/CIT-BIT проверены на официальных страницах авторов; русские версии цитируются отдельно. Не переносить эти условия на другие инструменты.

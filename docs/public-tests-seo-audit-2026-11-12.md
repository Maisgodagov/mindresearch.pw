## P1: конфликт robots.txt и клиентской загрузки

`robots.txt` запрещает весь `/api/`. Публичная статья есть в серверном HTML, но React создаёт приложение заново и получает её через `publicRequest`. Этот helper сначала зависит от `initializeAuth`, затем получает публичные данные API. Если запросы API недоступны, статья заменяется ошибкой, H1 исчезает, Metadata с `privatePage` устанавливает noindex/nofollow.

Воспроизведение на production в отдельном браузерном контексте с перехватом/блокировкой `/api/**`: исходная статья GAD-7 → текст «Не получилось загрузить данные / Network Error», H1 отсутствует, итоговый robots — noindex/nofollow. Обычный контекст сохраняет статью и index/follow. Это моделирование недоступности ресурсов, не снимок реального рендеринга Googlebot и не доказательство фактического удаления страниц из поиска.

Рекомендуется одновременно:

1. Отдавать начальные публичные данные вместе с HTML и использовать их при первом рендере, не стирая статью ради повторной загрузки.
2. Отделить чтение общедоступного контента от успешности обновления сессии пользователя.
3. Разрешить роботам только нужные публичные read-only маршруты API с сохранением ограничения остальных API. Не открывать автоматически весь `/api/public/`: там есть личные прохождения.
4. Не превращать временную сетевую ошибку существующей статьи в решение снять её с индексации. Реальный 404/снятие публикации обрабатывать отдельно.
5. Затем проверить URL Inspection/Search Console и рендеринг JavaScript в Яндекс Вебмастере.

Google учитывает отрендеренный HTML и предупреждает о блокировке ресурсов: https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics

## P2: сжатие и вес frontend

На странице GAD-7 браузер загрузил 21 JS-ресурс суммарно около 842 КБ тела. Основной `/assets/index-D8ubp4Gv.js` имеет Content-Length 759664 и отдан без Content-Encoding даже с Accept-Encoding gzip/deflate/br. Кэширование hashed assets уже включено (7 дней, public, immutable).

Включить gzip для JavaScript/CSS/JSON/SVG и проверить заголовки. Brotli — опционально, без необходимости менять весь стек. Затем измерить Lighthouse/PageSpeed и реальные CWV; в этом аудите не получены полевые LCP/INP/CLS и не выставляется фиктивная оценка скорости. После измерений оценить, какие части кабинета/аналитики можно не загружать посетителю публичного каталога.

- Произвольный неизвестный URL вне `/methods/` отдаёт оболочку 200 с noindex. В методиках уже правильный 404; общий fallback желательно привести к корректному статусу отдельно.

## Контент и структура

- Только для первых трёх тестов есть специально составленные SEO title; остальные используют шаблон научного названия. Для ключевых страниц стоит составить индивидуальные title/description под понятные намерения: например, «Тест на тревожность GAD-7 онлайн — шкала тревоги | mindresearch». Научное название в H1 сохраняется. Спрос и частоты Wordstat/показов в этом аудите не измерены.
- Description берётся из вводного текста; отдельные сниппеты можно сделать точнее: что оценивается, период, число вопросов, формат результата и необходимые ограничения. Лимиты символов не являются универсальным критерием качества и не гарантируют вид сниппета.
- Авторы исходных методик уже указаны, но это не авторство/экспертная проверка самого материала платформы. Нужны настоящие сведения о редакции, методе проверки расчётов, авторах/рецензентах статей и реальные даты изменений. Никаких вымышленных экспертов.
- При росте библиотеки сделать содержательные страницы широких тем с постоянными URL и ссылками на тесты. Нынешние фильтры noindex подходят для интерфейса, но не заменяют тематические посадочные страницы. Не создавать сотни пустых комбинаций фильтров.
- При росте более 20 записей отдельно пересмотреть SEO пагинации: текущий `?page=` считается фильтрованным/noindex с canonical на каталог. Проверить достижимость каждой статьи и не ограничиваться sitemap.
- Пользователь ранее просил убрать блок рекомендаций других тестов. Не возвращать его без согласования; тематические страницы и ссылки в подходящем контексте — отдельный вариант структуры.
- Наличие OG помогает превью в соцсетях, но само по себе не доказывает рост поисковых позиций. Не добавлять фиктивные рейтинги, диагнозы или разметку MedicalTest ради SEO.

О качестве и достоверности материалов: https://developers.google.com/search/docs/fundamentals/creating-helpful-content
